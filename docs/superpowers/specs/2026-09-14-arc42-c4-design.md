# PawCare Arc42 and C4 Architecture Documentation Design

## Purpose

Create a consistent architecture description for the PawCare static prototype using the Arc42 structure and the C4 model. The documentation must explain the current prototype truthfully, connect architecture decisions to existing UI, scripts, database schema and analysis documents, and avoid implying that a backend or real payment integration exists.

## Scope

This documentation covers the existing prototype scope:

- Pet profile management.
- Service catalog.
- Booking creation.
- Care process tracking.
- Appointment status tracking.
- Staff management.
- Payment and invoice screens.
- The SQLite-compatible database design.

Authentication, backend APIs, real-time updates, real payment gateways, medical records, analytics and production deployment remain outside the scope.

## Architecture approach

### Arc42

Create one readable Arc42 overview at `docs/architecture/arc42.md`. It will contain all twelve Arc42 sections with concise content:

1. Introduction and goals.
2. Constraints.
3. Context and scope.
4. Solution strategy.
5. Building block view.
6. Runtime view.
7. Deployment view.
8. Cross-cutting concepts.
9. Architecture decisions.
10. Quality requirements.
11. Risks and technical debt.
12. Glossary.

Each section will link to the more detailed C4, ERD, feature-analysis and design-system documents where appropriate.

### C4

Create the following Mermaid-based C4 documents under `docs/architecture/`:

- `c4-system-context.md`: PawCare as the system in scope, with pet owner, care staff, operations manager, browser/local server and payment gateway boundary explicitly marked as simulated/out of scope.
- `c4-container.md`: the static HTML UI, vanilla JavaScript navigation/verification, SQLite-compatible schema and Stitch/reference assets.
- `c4-component.md`: the logical UI/script groups for pet profiles, services, booking, care process, appointment tracking, staff management and payment/invoice.
- `c4-code.md`: actual file-level implementation mapping for pages, scripts, schema and documentation. It will be labelled as a lightweight code view because this repository is a static prototype rather than a class-based application.
- `c4-dynamic-flows.md`: Mermaid sequence diagrams for the main booking-to-payment journey and the care-process/staff assignment journey.

The C4 diagrams will use consistent element names, relationships and technology labels. The documents will state which elements are conceptual architecture groupings and which are actual files.

## Documentation structure

```text
docs/
├── architecture/
│   ├── README.md
│   ├── arc42.md
│   ├── c4-system-context.md
│   ├── c4-container.md
│   ├── c4-component.md
│   ├── c4-code.md
│   └── c4-dynamic-flows.md
├── analysis/
├── DESIGN.md
└── ERD.md
```

The architecture README will be the entry point and will explain the recommended reading order: Arc42 overview, C4 context, C4 containers, feature analysis, ERD and implementation files.

## Traceability

The architecture documentation will connect:

| Architecture concern | Existing evidence |
|---|---|
| Functional scope | `docs/petcare-system.xmind`, `docs/analysis/system-overview.md` |
| User behaviour | `docs/analysis/features/*.md` |
| UI structure | `pages/*.html`, `docs/DESIGN.md` |
| Navigation | `scripts/navigation.js` |
| Data structure | `database/schema.sql`, `docs/ERD.md` |
| Business constraints | `docs/analysis/business-rules.md` |
| Verification | `scripts/verify-project.ps1`, `scripts/verify-navigation.ps1` |

The root README will add an architecture section and links to the new documents without removing the existing UI, database or feature-analysis content.

## Verification

The implementation will be checked with:

- Existing project and navigation verification scripts.
- SQLite execution of `database/schema.sql`.
- `git diff --check`.
- A documentation verification block that checks all required Arc42/C4 files, Mermaid blocks, links and key scope statements.

## Out of scope for this change

- Adding a runtime backend.
- Migrating the static prototype to React, Vue or Next.js.
- Adding real authentication, payment processing or a production deployment.
- Introducing Structurizr, PlantUML or another diagram tool when Mermaid is already the repository convention.
- Creating new product features not present in the approved XMind scope.
